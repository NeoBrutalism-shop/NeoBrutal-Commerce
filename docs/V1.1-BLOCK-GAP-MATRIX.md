# v1.1 Block gap inventory

`docs/DEVELOPMENT-ROADMAP.md` remains the planning authority. This inventory records the evidence used to reconcile its Block target against the frozen Commerce 1.0 component registry, the current `storefront/blocks.json` catalog, and production/demo composition. It does not create a second roadmap or runtime authority.

Classification:

1. **First-class** — already has a stable Block contract and explicit live preview.
2. **Promote** — reusable identity is currently bundled inside a broader Block; promote from existing registered Components while keeping the compatibility Block intact.
3. **Equivalent** — an existing Block/component already carries the intended Commerce meaning; document the equivalence instead of duplicating it.
4. **Composable gap** — genuinely missing Block identity, but the composition can be built from existing registered Components without a new Component API.
5. **Component gap** — a distinct Block cannot be made truthful from the current 47 frozen Component contracts; defer until a deliberate component-contract decision.

## First expansion slice — product trust proof

Promote three read-only, production-backed identities from `trust-band`:

- `trust-strip` → `trust-strip`
- `testimonials` → `testimonials`
- `guarantee` → `guarantee`

Each promoted Block declares `promotedFrom: "trust-band"`. The existing `trust-band` remains unchanged in current Page compositions, so the v1.2 Page layer is not forced to migrate during the v1.1 expansion. Static/Page Lab conformance accounts for every Block either through direct Page composition or through an explicit promoted compatibility parent whose component set contains the promoted Block.

This slice changes documentation/showcase composition only. It adds no component IDs, models, actions, states, routes, provider assumptions, or Commerce 1.0 package/runtime surface.

## Fourth expansion slice — subscription management

Promote the production-backed `subscription-management` identity from `ownership-operations`:

- `subscription-management` → `subscription-management`

The promoted Block declares `promotedFrom: "ownership-operations"`. The production `/account/license/:id` route already renders the frozen `subscription-management` component and its normalized `subscription.get`, `subscription.cancel`, and `subscription.resume` actions, while `ownership-operations` remains the Page-composed compatibility parent for plan change, transfer/gift, subscription, and renewal concerns.

The promoted live preview exercises the safe reversible path `active` → `cancel_at_period_end` → `active`. Cancel-at-period-end keeps the already-paid term visible through the provider-returned date and does not imply license revocation. The canonical terminal `cancelled` and recovery-required `past_due` states remain represented by the frozen component state contract rather than being fabricated as local demo transitions.

After this slice, the v1.1 Block catalog contains 25 reusable Blocks: 18 Page-composed compatibility Blocks plus 7 promoted reusable Blocks. Static, Page Lab, and browser conformance require exact 25/25 documentation and live-preview coverage, exact promotion-family lineage, and browser proof of the cancel/resume state transition.

This slice changes only documentation/showcase composition. It adds no component IDs, models, actions, states, routes, provider assumptions, Commerce exports, or Commerce 1.0 package/runtime behavior.
