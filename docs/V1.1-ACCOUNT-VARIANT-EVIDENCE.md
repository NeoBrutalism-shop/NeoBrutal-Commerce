# v1.1 Account + ownership variant evidence

This report is an extension to `docs/V1.1-COMPONENT-DEMO-DEPTH-AUDIT.md`. It records the fifth source-audited variant-evidence batch without rewriting the certified four-batch baseline. Commerce remains frozen at v1.0.0: this work does not add component IDs, models, actions, canonical states, routes, package exports, tokens, or provider semantics.

## Combined status

The certified four-batch baseline remains **28 / 47** variant-complete components and **65** authoritative variants. The Account + ownership extension promotes exactly ten additional components and 35 additional showcase labels, yielding the current combined status:

- **38 / 47 components** variant-complete; **9 / 47** remain partial.
- **100 authoritative variants** total.
- Proof split: **56 rendered**, **36 canonical-state-backed**, **4 responsive-backed**, **2 interaction-backed**, and **2 action-backed**.
- The existing 43 / 47 source-backed implementation-evidence coverage is unchanged.
- The frozen Commerce contract remains 47 components, 14 exports, 21 canonical actions, 42 documented live states, and 40 semantic tokens.

Machine-readable Account proof lives in `storefront/component-variant-evidence-account.json`. The corresponding audit promotion lives in `storefront/component-demo-depth-account.json`. `component-variant-evidence.js` combines the certified baseline with the Account shard and rejects duplicate batch/component membership. `component-depth-variant-extension.js` waits for both the base depth audit and combined variant evidence before promoting only the ten proven `All variants` cells.

## Fifth variant-evidence batch — Account + ownership

Exactly ten components are promoted:

1. `account-nav` — `current`, `inactive`
2. `download-row` — `eligible`, `unavailable`
3. `license-card` — `active`, `limited`, `expired context`
4. `license-status` — `active`, `grace`, `expired`, `cancelled`, `refunded`
5. `update-eligibility` — `active`, `grace`, `expired`
6. `renewal-state` — `active`, `grace`, `expired`, `cancelled`, `past_due`
7. `plan-change` — `ready`, `quoted`, `processing`, `complete`, `failed`
8. `ownership-transfer` — `ready`, `processing`, `complete`, `failed`, `pending invitation`
9. `subscription-management` — `active`, `cancel_at_period_end`, `cancelled`, `past_due`
10. `ownership-timeline` — `chronological event list`

The Account batch contains **35** exact labels: **8 rendered**, **26 canonical-state-backed**, and **1 action-backed**. Together with the previous four batches this produces the 100-variant combined split above.

### Rendered proof

`account-nav` uses real navigation links and `aria-current="page"` for current location instead of treating navigation as a cosmetic button state. `download-row` distinguishes an available download from an unavailable entitlement by keeping the unavailable action disabled and explicitly tying the consequence to normalized entitlement data. `license-card` uses shipping license-card anatomy for active, capacity-limited, and expired-context presentations without creating new lifecycle states. `ownership-timeline` uses the shipping ordered-list anatomy and labels its sample events as provider-returned evidence rather than reconstructed history.

### Canonical-state proof

`license-status`, `update-eligibility`, `renewal-state`, `plan-change`, `ownership-transfer`, and `subscription-management` reuse the exact canonical state matrices already owned by `storefront/component-states.json`. No duplicate state markup is created.

Showcase labels are normalized only for variant identity. Canonical IDs remain untouched. For example, showcase `past_due` becomes variant identity `past-due`, but its proof references canonical state ID `past_due`; `cancel_at_period_end` similarly normalizes to `cancel-at-period-end` while preserving canonical state ID `cancel_at_period_end`. The checker requires normalized equivalence and also requires the exact state ID to exist in the authoritative state registry.

### Action-backed proof

`ownership-transfer:pending invitation` is **not** promoted as a fifth canonical ownership-transfer state. A pending invitation is an authoritative result of `license.transfer.create`, represented by `OwnershipTransferView`, while the canonical ownership-transfer lifecycle remains `ready`, `processing`, `complete`, and `failed`. This keeps the important semantic boundary that creating an invitation does not itself mean ownership moved.

## Four deliberate Account exclusions

Four Account components remain variant-partial because at least one showcase label cannot currently be proved from the frozen Commerce v1.0 contract. They are intentionally excluded instead of receiving decorative or fabricated proof.

1. `purchase-history-row` — showcase `paid order` does not exactly match frozen `OrderStatus`; a successful order is `complete`, not `paid`.
2. `invoice-history` — showcase `open` is not a frozen `InvoiceStatus`; the contract permits `paid`, `refunded`, and `void`.
3. `activation-row` — showcase `removable` has no canonical activation removal/deactivation action. Frozen v1.0 only exposes `license.activations.list` for this component.
4. `seat-assignment` — showcase `capacity reached` has no capacity value in the component's frozen model/action result authority. Seat list/assign/remove operations exist, but capacity must not be guessed from unrelated records.

Each exclusion is encoded in `storefront/component-demo-depth-account.json` with a concrete reason, and CI fails if an excluded component is accidentally promoted. The checks also fail in the opposite direction when relevant frozen authority appears—for example, if a real activation-removal action is added, the exclusion must be deliberately revisited rather than silently persisting.

## Browser and accessibility evidence

`tests/component-variant-evidence-account-v11.spec.mjs` adds bounded Browser QA for the fifth batch. It verifies the combined 38 / 47 and 100-variant counters, exactly ten Account promotions and four Account exclusions, all eight rendered samples, all 26 canonical state references, the `license.transfer.create` + `OwnershipTransferView` pending-invitation result proof, keyboard operation, tactile downward hover behavior, dark/narrow containment, and targeted WCAG A/AA Axe coverage across all ten promoted Account cards.

The existing `tests/component-variant-evidence-v11.spec.mjs` remains the accumulated v1.1 suite. Its existing semantic, responsive, interaction, keyboard, tactile, dark-mode, and Axe test bodies are preserved; only the shared accumulated evidence counters advance from the certified four-batch baseline to the five-batch combined result.

## Authority boundary

The evidence hierarchy remains unchanged:

`storefront/components.json` + `storefront/states.json` + `src/contracts/index.d.ts` + `src/actions/runtime.js` → frozen Commerce runtime authority

`storefront/component-showcase.json` → authoritative showcase labels and presentation guidance

`storefront/component-states.json` → canonical live state examples

`storefront/component-variant-evidence.json` + `storefront/component-variant-evidence-account.json` → evidence only

`storefront/component-demo-depth.json` + `storefront/component-demo-depth-account.json` → audit evidence only

No evidence file is allowed to create a new production state, action, model, provider result, price, entitlement, activation command, or capacity fact merely to make the coverage matrix look complete.
