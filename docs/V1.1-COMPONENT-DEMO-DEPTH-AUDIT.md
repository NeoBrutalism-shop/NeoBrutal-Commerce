# v1.1 Component demo depth audit

`docs/DEVELOPMENT-ROADMAP.md` remains the planning authority. This document records the current evidence for its 47-component demo-depth exit gate; it does not redefine Commerce runtime models, actions, states, interaction laws, or the roadmap.

The machine-readable audit companion is `storefront/component-demo-depth.json`. Its role is **audit evidence only**. Runtime component semantics remain in `storefront/components.json` and `storefront/states.json`; interaction physics remain in `storefront/interactions.json`; presentation taxonomies remain in `storefront/component-showcase.json`.

Implementation evidence is intentionally split by audited batch so provenance remains inspectable instead of being rewritten as coverage expands. `storefront/component-demo-implementation.json` remains the original 12-component stateful/high-risk evidence file. `storefront/component-demo-implementation-product.json` is the second 7-component product/storefront evidence file. Both remain **implementation evidence only**: they point to shipping selectors/tokens and expose copy-ready HTML/CSS/JS, but neither becomes a second runtime authority.

## Status meanings

- **complete** — current repository evidence satisfies this checklist item for the component.
- **partial** — some relevant evidence exists, but the roadmap asks for more explicit per-component proof.
- **missing** — the current component demo has no dedicated evidence for the checklist item.
- **not-applicable** — the frozen component contract does not own that concern; the audit must not invent it merely to fill a matrix.

## Second implementation-depth batch

The second bounded batch covers seven product/storefront components whose real shipping implementation is already concentrated in `src/components/product.css` and `src/components/product-detail.css`:

1. `product-card`
2. `badge`
3. `price-block`
4. `product-detail`
5. `product-gallery`
6. `license-selector`
7. `renewal-note`

Their evidence lives in `storefront/component-demo-implementation-product.json`. Every declared selector must exist in the referenced shipping source. Every token must exist in `src/tokens.css` and be used through `var(...)` by referenced component CSS. Every JavaScript snippet is syntax-checked as an ES module. `product-card` must preserve the frozen `cart.add` action; actionless product components are rejected if their snippets invent Commerce mutations. Product-gallery evidence keeps real button/`aria-pressed` anatomy, and license-selector evidence keeps an inspectable selected radio capacity.

The audit runtime reads the ordered `implementationBatches` lineage from `storefront/component-demo-depth.json`, validates each evidence file against its exact batch membership, rejects duplicate component evidence, and derives accumulated implementation coverage from the union. The legacy `nextImplementationBatch` field remains the exact first 12-component stateful set for compatibility and provenance; it is not repurposed to erase batch history.

The remaining partial criteria for all 47 components—variants, edge-state applicability, explicit dual-theme proof, full desktop/tablet/mobile proof, interaction-state proof, implementation API detail, and LLM usage depth—remain partial until their own inspectable evidence ships. This slice promotes only Design tokens used and Copy-ready HTML / CSS / JS for the seven components above.

## Acceptance rule for future depth slices

A component moves from `partial` or `missing` only when the repository contains inspectable evidence for that exact checklist item and Quality/Browser QA enforce it. The audit matrix must continue to cover all 47 frozen component IDs exactly, implementation batches must remain ordered and non-overlapping, and no depth work may modify the frozen Commerce 1.0 package/runtime contract merely to make documentation easier.
