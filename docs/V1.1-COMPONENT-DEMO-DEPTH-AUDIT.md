# v1.1 Component demo depth audit

`docs/DEVELOPMENT-ROADMAP.md` remains the planning authority. This document records the current evidence for its 47-component demo-depth exit gate; it does not redefine Commerce runtime models, actions, states, interaction laws, or the roadmap.

The machine-readable audit companion is `storefront/component-demo-depth.json`. Its role is **audit evidence only**. Runtime component semantics remain in `storefront/components.json` and `storefront/states.json`; interaction physics remain in `storefront/interactions.json`; presentation taxonomies remain in `storefront/component-showcase.json`.

Implementation evidence is intentionally split by audited batch so provenance remains inspectable instead of being rewritten as coverage expands. `storefront/component-demo-implementation.json` remains the original 12-component stateful/high-risk evidence file. `storefront/component-demo-implementation-product.json` remains the second 7-component product/storefront evidence file. `storefront/component-demo-implementation-trust-pricing.json` remains the third 7-component trust/review/pricing evidence file. `storefront/component-demo-implementation-cart-checkout.json` remains the fourth 7-component cart/checkout evidence file. `storefront/component-demo-implementation-account-ownership.json` is the fifth 10-component account/ownership evidence file. All five remain **implementation evidence only**: they point to shipping selectors/tokens and expose copy-ready HTML/CSS/JS, but none becomes a second runtime authority.

Variant evidence is separate from implementation evidence. `storefront/component-variant-evidence.json` now accumulates three ordered proof batches and supports three explicit proof kinds: **rendered** proof for genuine presentation alternatives, **canonical-state** proof when a documented variant label is exactly an existing canonical state, and **responsive-backed** proof when multiple documented labels describe the same semantic component under different authoritative viewport behavior. Variant names remain owned by `storefront/component-showcase.json`; canonical states remain owned by `storefront/component-states.json`; responsive behavior remains owned by each showcase component's `responsiveMode` plus shipping CSS. Variant evidence may prove those authorities, but it may not invent a second taxonomy, duplicate state truth, or clone responsive presentations as fake cosmetic markup.

## Status meanings

- **complete** — current repository evidence satisfies this checklist item for the component.
- **partial** — some relevant evidence exists, but the roadmap asks for more explicit per-component proof.
- **missing** — the current component demo has no dedicated evidence for the checklist item.
- **not-applicable** — the frozen component contract does not own that concern; the audit must not invent it merely to fill a matrix.

## Third variant-evidence batch

The third variant-proof slice covers the complete three-component **Pricing** family and exactly six authoritative labels:

1. `pricing-tier` — `default`, `featured`
2. `plan-comparison` — `desktop table`, `narrow scroll container`
3. `bundle-builder` — `no extras`, `selected extras`

`pricing-tier` and `bundle-builder` are genuine presentation/state alternatives and therefore add four **rendered** proofs using the existing shipping anatomy in `src/components/pricing.css`. The default plan uses `.nbc-plan-card` without featured state, while the featured plan uses `.nbc-plan-card[data-featured="true"]` and `.nbc-plan-ribbon`. Both keep price, production-site capacity, and the 12-month update term visible. Bundle-builder's `no extras` proof starts both native checkboxes unchecked at the $49 base total; `selected extras` visibly checks one optional extra and shows the resulting $69 total. These samples demonstrate presentation consequence only and do not dispatch or invent Commerce actions.

`plan-comparison` is deliberately modeled as **responsive-backed** rather than two rendered copies. `desktop table` and `narrow scroll container` are the same semantic `.nbc-compare` table inside the same focusable `.nbc-compare-wrap`; the authoritative showcase declares `responsiveMode: contained-scroll`, and shipping CSS gives the table `min-width:44rem` inside `overflow-x:auto`. The manifest therefore stores no duplicate table markup. Both labels reference the live wrapper/table selectors, their authoritative responsive mode, and their target viewport. Browser QA proves the real live preview and `/pricing/` route at desktop and 360px width, requires the narrow wrapper to contain horizontal overflow locally, requires the document itself not to overflow, and verifies the wrapper remains keyboard-focusable. That is evidence of responsive behavior, not a new component state.

Across all three batches, `storefront/component-variant-evidence.json` now proves exactly **37** authoritative variants across **16** components: **32 rendered**, **3 canonical-state-backed**, and **2 responsive-backed**. The checker rejects unknown/duplicate variants, batch overlap, taxonomy mismatch, canonical-state references to unknown state IDs, rendered markup on canonical-state or responsive-backed proofs, responsive-mode drift from `storefront/component-showcase.json`, unsupported responsive viewports, missing live selectors, or state/responsive metadata on rendered presentation proofs. It also preserves every first- and second-batch semantic assertion while source-auditing Pricing anatomy against `storefront/component-demo-implementation-trust-pricing.json`, `src/components/pricing.css`, and the live component explorer.

Browser QA switches all 32 rendered samples in bounded scenarios, verifies exactly one pressed rendered choice at a time, separately exercises the three canonical-state-backed product-media variants, and proves the two responsive-backed plan-comparison labels against the same semantic table at desktop and narrow widths. Keyboard activation, focus, downward tactile compression, dark theme, narrow width, Axe A/AA, and page-overflow checks remain enforced. These 16 components therefore move `All variants` to complete; the remaining 31 stay partial until equivalent inspectable evidence ships.

The remaining partial criteria for all 47 components—edge-state applicability, explicit dual-theme proof, full desktop/tablet/mobile proof, interaction-state proof, implementation API detail, and LLM usage depth—remain partial until their own inspectable evidence ships. Implementation evidence remains at 43 / 47 with four explicit gaps: `promo-band`, `invoice-details`, `component-contract`, and `tokens`. Those four remain missing because the current repository does not yet provide a distinct shipping component selector/authority suitable for honest implementation evidence; showcase-only composition is not promoted as production component proof.

## Acceptance rule for future depth slices

A component moves from `partial` or `missing` only when the repository contains inspectable evidence for that exact checklist item and Quality/Browser QA enforce it. The audit matrix must continue to cover all 47 frozen component IDs exactly, implementation batches must remain ordered and non-overlapping, and variant evidence must remain exactly aligned to `storefront/component-showcase.json`.

Rendered proof must use real shipping anatomy; canonical-state-backed proof must reference rather than duplicate `storefront/component-states.json`; responsive-backed proof must reference the existing live preview plus the authoritative `responsiveMode` and be demonstrated at the declared viewport in Browser QA rather than cloning markup. No depth work may modify the frozen Commerce 1.0 package/runtime contract merely to make documentation easier.
