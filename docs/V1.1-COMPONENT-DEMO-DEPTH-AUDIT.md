# v1.1 Component demo depth audit

`docs/DEVELOPMENT-ROADMAP.md` remains the planning authority. This document records the current evidence for its 47-component demo-depth exit gate; it does not redefine Commerce runtime models, actions, states, interaction laws, or the roadmap.

The machine-readable audit companion is `storefront/component-demo-depth.json`. Its role is **audit evidence only**. Runtime component semantics remain in `storefront/components.json` and `storefront/states.json`; interaction physics remain in `storefront/interactions.json`; presentation taxonomies remain in `storefront/component-showcase.json`.

Implementation evidence is intentionally split by audited batch so provenance remains inspectable instead of being rewritten as coverage expands. `storefront/component-demo-implementation.json` remains the original 12-component stateful/high-risk evidence file. `storefront/component-demo-implementation-product.json` remains the second 7-component product/storefront evidence file. `storefront/component-demo-implementation-trust-pricing.json` remains the third 7-component trust/review/pricing evidence file. `storefront/component-demo-implementation-cart-checkout.json` remains the fourth 7-component cart/checkout evidence file. `storefront/component-demo-implementation-account-ownership.json` is the fifth 10-component account/ownership evidence file. All five remain **implementation evidence only**: they point to shipping selectors/tokens and expose copy-ready HTML/CSS/JS, but none becomes a second runtime authority.

Variant evidence is separate from implementation evidence. `storefront/component-variant-evidence.json` records rendered proof for the first five-component storefront-core variant batch. Variant names remain owned by `storefront/component-showcase.json`; the variant evidence file may prove those names visually, but it may not invent a second variant taxonomy or redefine canonical states/responsive modes as cosmetic variants.

## Status meanings

- **complete** — current repository evidence satisfies this checklist item for the component.
- **partial** — some relevant evidence exists, but the roadmap asks for more explicit per-component proof.
- **missing** — the current component demo has no dedicated evidence for the checklist item.
- **not-applicable** — the frozen component contract does not own that concern; the audit must not invent it merely to fill a matrix.

## Fourth implementation-depth batch

The fourth bounded batch covers seven cart/checkout components whose shipping anatomy is concentrated in `src/components/cart.css`, `src/components/checkout.css`, and `src/components/summary.css`:

1. `cart-item`
2. `order-summary`
3. `coupon`
4. `checkout-field`
5. `payment-method`
6. `order-confirmation`
7. `receipt`

Their evidence lives in `storefront/component-demo-implementation-cart-checkout.json`. `cart-item` preserves the frozen `cart.remove` payload shape with both normalized `cartId` and `lineId`. Coupon application never invents discount or tax results locally: it requotes through canonical `checkout.quote` with normalized `couponCodes` and exposes the returned quote as authoritative. `order-summary` renders normalized quote totals rather than recalculating provider truth. `checkout-field` keeps native label/input validity and autocomplete semantics. `payment-method` remains local normalized selection state and is rejected if it invents a Commerce mutation. `order-confirmation` requires a normalized complete order and explicitly does not imply entitlement or download delivery. `receipt` keeps order total and invoice number/status as distinct normalized records rather than collapsing payment/order/invoice concepts.

## Fifth implementation-depth batch

The fifth bounded batch covers ten account/ownership components whose shipping anatomy is concentrated in `src/components/account.css`, `src/components/license.css`, and `src/components/lifecycle.css`:

1. `download-entitlement`
2. `account-nav`
3. `download-row`
4. `purchase-history-row`
5. `license-card`
6. `invoice-history`
7. `activation-row`
8. `seat-assignment`
9. `ownership-timeline`
10. `ownership-lifecycle`

Their evidence lives in `storefront/component-demo-implementation-account-ownership.json`. Download surfaces request canonical `download.create` only from normalized entitlement/release identity and use the returned signed URL rather than treating a URL as permanent entitlement state. Account navigation uses real navigation anatomy and exposes the current section. Purchase history stays transaction-only; it does not infer license or subscription state from an order. `license-card` keeps normalized `LicenseView` and `EntitlementView` identity separate from subscription billing. Invoice history queries canonical `invoice.list` and renders returned invoice number/status/total instead of reconstructing billing state.

Activation evidence is deliberately query-only through `license.activations.list`: the frozen Commerce 1.0 action set has no activation-removal mutation, so this implementation evidence does not copy the decorative `DEACTIVATE` affordance from the showcase preview into a fake command. Seat management preserves the distinct `license.seats.list`, `seat.assign`, and `seat.remove` contracts and their exact `licenseId`/`seatId`/assignee payloads. Ownership timeline renders returned `license.history.list` events instead of reconstructing historical events from current state. `ownership-lifecycle` keeps license, entitlement, subscription, seat, activation, and transfer concepts semantically separate.

The audit runtime reads the ordered `implementationBatches` lineage from `storefront/component-demo-depth.json`, validates every evidence file against its exact batch membership, rejects duplicate component evidence, and derives accumulated implementation coverage from the union. The legacy `nextImplementationBatch` field remains the exact first 12-component stateful set for compatibility and provenance; it is not repurposed to erase batch history.

## First variant-evidence batch

The first variant-proof slice covers five storefront-core components and exactly 13 variant samples:

1. `product-card` — `default`, `accent badge`, `primary action`
2. `trust-strip` — `check-mark fact`, `policy/support fact`
3. `promo-band` — `informational`, `highlighted offer`
4. `badge` — `default`, `coral`, `lime`
5. `price-block` — `one-time`, `recurring`, `license-scoped`

Their proof lives in `storefront/component-variant-evidence.json` and is rendered by `component-variant-evidence.js`. The variant IDs are normalized only for machine identity; their authoritative human labels remain the exact labels in `storefront/component-showcase.json`. Every variant has its own explicit rendered sample and is selectable through mutually exclusive `aria-pressed` controls. The dedicated checker rejects unknown, duplicated, or missing variants and verifies exact equality with the showcase taxonomy.

This slice also protects semantic honesty. The product-card primary-action variant uses the real tactile primary-action anatomy. Trust-strip policy/support proof is explicitly supplied-data/policy backed. Promo-band proofs state real commercial information without fabricated urgency or scarcity. Badge variants use the shipping default/coral/lime classes. Price-block variants visibly distinguish one-time purchase, recurring renewal cadence, and license-scoped capacity/update consequence. These are presentation variants only; canonical states, responsive modes, and interaction states remain separate authorities and are not relabeled as variants to inflate coverage.

Browser QA switches all 13 samples, verifies exactly one pressed choice at a time, checks keyboard activation and focus, exercises the downward tactile compression grammar, runs the proof in dark theme, checks Axe A/AA, and verifies narrow-screen containment. Only these five components therefore move `All variants` to complete. The other 42 remain partial until equivalent explicit proof ships.

The remaining partial criteria for all 47 components—edge-state applicability, explicit dual-theme proof, full desktop/tablet/mobile proof, interaction-state proof, implementation API detail, and LLM usage depth—remain partial until their own inspectable evidence ships. Implementation evidence remains at 43 / 47 with four explicit gaps: `promo-band`, `invoice-details`, `component-contract`, and `tokens`. Those four remain missing because the current repository does not yet provide a distinct shipping component selector/authority suitable for honest implementation evidence; showcase-only composition is not promoted as production component proof.

## Acceptance rule for future depth slices

A component moves from `partial` or `missing` only when the repository contains inspectable evidence for that exact checklist item and Quality/Browser QA enforce it. The audit matrix must continue to cover all 47 frozen component IDs exactly, implementation batches must remain ordered and non-overlapping, variant evidence must remain exactly aligned to `storefront/component-showcase.json`, and no depth work may modify the frozen Commerce 1.0 package/runtime contract merely to make documentation easier.
