# v1.1 Component demo depth audit

`docs/DEVELOPMENT-ROADMAP.md` remains the planning authority. This document records the current evidence for its 47-component demo-depth exit gate; it does not redefine Commerce runtime models, actions, states, interaction laws, or the roadmap.

The machine-readable companion is `storefront/component-demo-depth.json`. Its role is **audit evidence only**. Runtime component semantics remain in `storefront/components.json` and `storefront/states.json`; interaction physics remain in `storefront/interactions.json`; presentation taxonomies remain in `storefront/component-showcase.json`.

## Status meanings

- **complete** — current repository evidence satisfies this checklist item for the component.
- **partial** — some relevant evidence exists, but the roadmap asks for more explicit per-component proof.
- **missing** — the current component demo has no dedicated evidence for the checklist item.
- **not-applicable** — the frozen component contract does not own that concern; the audit must not invent it merely to fill a matrix.

## First implementation-depth batch

The first focused batch is the 12 stateful/high-risk component families because their canonical states and consequence semantics are already authoritative and therefore provide the strongest foundation for deeper demos:

1. `product-media`
2. `checkout-steps`
3. `payment-failure`
4. `payment-recovery`
5. `processing-state`
6. `license-status`
7. `update-eligibility`
8. `renewal-state`
9. `plan-change`
10. `ownership-transfer`
11. `subscription-management`
12. `system-states`

For this batch, deeper evidence must reference—not duplicate—the existing authorities. State IDs/consequences come from `storefront/components.json`, `storefront/component-states.json`, and `storefront/states.json`. Tactile/result/loading behavior comes from `storefront/interactions.json`. Token usage must point to real CSS variables and source stylesheets. Copy-ready examples must be derived from shipping/demo anatomy and preserve canonical action/state names.

## Acceptance rule for future depth slices

A component moves from `partial` or `missing` only when the repository contains inspectable evidence for that exact checklist item and Quality/Browser QA enforce it. The audit matrix must continue to cover all 47 frozen component IDs exactly, and no depth work may modify the frozen Commerce 1.0 package/runtime contract merely to make documentation easier.
