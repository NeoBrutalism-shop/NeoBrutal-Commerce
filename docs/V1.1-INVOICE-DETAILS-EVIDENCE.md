# v1.1 Invoice details residual evidence

This slice starts from independently certified `main` SHA `24563484a9993c6c994f24114dc7956d3b93f694` after PR #50. It closes the evidence gap around `invoice-details` without changing the frozen Commerce 1.0 runtime/API or prematurely rewriting the already-certified aggregate audit checkpoints.

## Why this is a staged evidence slice

After the System + foundation variant batch, the accumulated certified checkpoint is:

- 42 / 47 components with promoted variant evidence
- 117 exact documented variants
- 42 variant-complete / 5 variant-partial components
- 43 components in the accumulated implementation-evidence lineage across five certified implementation batches

`invoice-details` is the only residual variant-partial component whose documented variants can be demonstrated truthfully from existing frozen input and model authority without adding an action, canonical state, provider outcome, tax rule, jurisdiction rule, or billing guess.

This slice therefore adds permanent source-backed evidence first. It intentionally leaves the aggregate `42/117`, `42 complete / 5 partial`, and `43 components / 5 implementation batches` checkpoints unchanged until a separate promotion step reviews and adopts this evidence into the accumulated audit.

## Frozen authority used

`storefront/components.json` defines `invoice-details` as an actionless input component backed by `CheckoutQuoteView` and `InvoiceView`.

`src/contracts/index.d.ts` defines:

```ts
interface InvoiceDetails {
  requested: boolean;
  legalName?: string;
  billingAddress?: BillingAddress;
  taxId?: string;
}
```

`src/components/cart.css` already exports the reusable `.nbc-checkout-field` anatomy through `@neobrutal/commerce/styles.css`.

No provider-specific payment or invoicing contract is introduced here.

## Exact documented variants

The residual variant manifest proves the three existing `storefront/component-showcase.json` labels exactly:

1. **individual** — business invoice details are not requested; provider-normalized quote values remain authoritative for tax and totals.
2. **business invoice** — legal-name and tax-ID inputs are visible; the UI explicitly does not predict tax treatment or invoice status.
3. **validation** — local recoverable input validation is shown with `required`, `aria-invalid`, and `aria-describedby`; validation does not fabricate provider results.

All three proofs are declarative rendered examples. No tax rate, VAT rate, sales-tax rate, jurisdiction, invoice status, or payment result is synthesized.

## Copy-ready implementation evidence

`storefront/component-demo-implementation-invoice-details.json` documents:

- shipping selectors from `src/components/cart.css`

## Remaining Account blockers

This slice does not alter the four intentionally unresolved Account variant mismatches:

- `purchase-history-row`: `paid order` does not exactly match frozen successful `OrderStatus=complete`.
- `invoice-history`: documented `open` is not a frozen `InvoiceStatus` (`paid | refunded | void`).

Those require their own source-backed reconciliation. They are not weakened or silently reinterpreted here.
